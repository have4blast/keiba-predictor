# 要件定義 — 第3サイクル (0003_automation)

## 背景

0001・0002 で予測パイプラインと品質基盤を整備した。  
第3サイクルでは **CI/CD による自動化** と **Docker による環境再現性** を実現し、  
毎日の手動操作を不要にする。

---

## B-1. GitHub Actions 自動化 — 機能要件

| ID | 要件 | 優先度 |
|----|------|--------|
| B-FR-01 | 毎日 08:00 JST に翌日出走表を自動取得するワークフローを実装する | 高 |
| B-FR-02 | 毎日 08:30 JST に特徴量を自動生成するワークフローを実装する | 高 |
| B-FR-03 | 毎週月曜 02:00 JST にモデルを自動再学習するワークフローを実装する | 高 |
| B-FR-04 | 再学習後に AUC を前回と比較し、退行（差分 > 0.02）を検知してアラートを出す | 高 |
| B-FR-05 | ワークフロー失敗時に GitHub の Issues または Slack に通知する | 中 |
| B-FR-06 | データ品質チェック（`validate_data.py`）を各ワークフローの前後に実行する | 中 |

## B-1. 非機能要件

| ID | 要件 |
|----|------|
| B-NFR-01 | GitHub Secrets に DB・モデルを格納するのではなく、`data/` と `models/` はワークフロー実行環境にキャッシュする |
| B-NFR-02 | ワークフローのタイムアウトは 30 分以内 |
| B-NFR-03 | 失敗時はロールバック（前回モデルを維持）し、本番を壊さない |

---

## B-2. Docker コンテナ化 — 機能要件

| ID | 要件 | 優先度 |
|----|------|--------|
| B-FR-07 | `Dockerfile` でアプリ全体（依存・コード）をコンテナ化する | 高 |
| B-FR-08 | `docker-compose.yml` でダッシュボードとスクレイピングを別サービスに分離する | 高 |
| B-FR-09 | `data/` と `models/` をホスト側ボリュームにマウントして永続化する | 高 |
| B-FR-10 | `.env` ファイルを `docker-compose.yml` から自動読み込みする | 中 |

## B-2. 非機能要件

| ID | 要件 |
|----|------|
| B-NFR-04 | ベースイメージは `python:3.11-slim` を使用しイメージサイズを最小化する |
| B-NFR-05 | `docker compose up -d dashboard` 一コマンドでダッシュボードを起動できること |

---

## B-3. LINE Notify 予測通知 — 機能要件

| ID | 要件 | 優先度 |
|----|------|--------|
| B-FR-11 | 毎日 09:00 JST にその日の全レース上位3頭をまとめて LINE に送信する | 中 |
| B-FR-12 | 通知には「レース名・本命・対抗・単穴・勝利スコア」を含める | 中 |
| B-FR-13 | LINE Token は `.env` / GitHub Secrets に格納し、コードにハードコードしない | 高 |

## B-3. 非機能要件

| ID | 要件 |
|----|------|
| B-NFR-06 | LINE Notify API は `requests.post` で直接呼び出し（外部 SDK 不要） |
| B-NFR-07 | 通知失敗時はログに記録し、パイプラインを中断しない |

---

## 対象外スコープ

- Kubernetes / ECS デプロイ（第4サイクル候補）
- Slack 通知（LINE に絞る）
- プロキシローテーション（環境依存のため別途検討）
